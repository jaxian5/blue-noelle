## Security correction during QA

The original baseline had unnecessary PostgreSQL privileges inherited by `anon`, and more direct `authenticated` write privileges than Phase 1 requires. RLS policies prevented unauthorized rows, but least-privilege principle still calls for explicit revocation.

**Applied live:** `20261025042230_phase1_least_privilege_table_grants.sql`.

- Remove `PUBLIC` and `anon` grants from all 19 application tables.
- Remove direct authenticated INSERT/UPDATE/DELETE on User, Class, ClassMembership and ClassActionLog. Their trusted mutations continue to run through secured Auth triggers and class-scoped RPCs.
- Disable hard deletion of academic Subject and Assignment; leave Phase 2's column-level soft-delete grants and intended schedule operations.
- Verify essential authenticated SELECT and Phase 2 INSERT privileges still work.
- **Post-migration registration regression PASS:** Admin invite issuance, Student PENDING redemption, own membership read under `authenticated`. Test transaction rolled back.
- Current Supabase advisor: no uncovered public-RLS table issues, but INFO on intentionally denied future-phase tables, and WARN `auth_leaked_password_protection`. Leaked-password protection requires a paid Supabase plan; on Free it is a documented limitation, not a reason to secretly add unsafe custom password storage.

## Phase 1 release gate, in order

1. **Trusted bootstrap:** identify the authorized real Supabase Auth account and the intended actual classroom; explicitly approve first Admin role assignment (not via a public browser RPC). Do not assume the only Auth account should be Admin or the sample class is the production class.
2. **Live invite:** that Admin signs into the deployed site and generates a limited-use Student invitation; record only hash in the DB.
3. **Live student:** a different real account confirms email, redeems invite, sees PENDING and cannot read classwork.
4. **Live officer review:** test Admin approval, and add/test a separately provisioned Moderator to exercise genuine Moderator queue and rejection.
5. **Live ACTIVE access:** Student sees ACTIVE membership on the account page; verify own-class reads from browser using signed-in JWT and cross-class access denied.
6. **Negative and recovery:** wrong/expired/revoked codes, duplicate requests, replay, reset password, sign out/in, mobile and failed network.
7. **Before approval:** implement practical invite revocation or explicitly defer it through a documented policy, address rejected-registration reset/appeal, clean confusing inherited demo routes, and obtain user's approval of the Phase 1 gate.

**Recommendation:** Do **not** formally approve Phase 1 or begin Phase 2 integration yet. The database behavior passes comprehensive synthetic tests, but the live first-Admin/student/moderator end-to-end test is still unperformed. Continue Phase 1 without upgrading Supabase Free solely to silence the leaked-password advisory.
