# Phase 3: Private Submissions and Versioned File Storage
**Started:** October 25, 2026. **Status:** implemented on a review branch, awaiting CI and live browser/storage acceptance.

## Architecture and safety

- Private Supabase Storage bucket **`bn-submissions`** (public=false), per-file bucket cap **40 MiB** (Free Plan compatible).
- Object keys are generated by a private, authorized PostgreSQL function, not user-supplied URLs or filenames. Structure: `classId/assignmentId/submissionId/versionId/fileId` (UUIDs only).
- `storage.objects` RLS permits INSERT only for the exact **PENDING** metadata row owned by the current ACTIVE Student/group-member uploader, and SELECT for READY files only by the owning ACTIVE Student/group members or ACTIVE Admin/Moderator of the assignment's class. Pending SELECT/DELETE allow only the original uploader to clean up their own incomplete uploads. No broad UPDATE/upsert permission.
- Dedicated version and file states: `SubmissionVersion.upload_state = UPLOADING | READY`, `File.upload_state = PENDING | READY`. Only actual Storage metadata with matching size and MIME allows transition to READY, through a guarded finalization RPC. This is **not antivirus content inspection**.
- `Submission` statuses: DRAFT, SUBMITTED, DELETED. Exactly one individual Student or Group owner, never both (existing XOR invariant). New revisions use separate immutable version/file IDs. Final SUBMIT is an atomic RPC that only succeeds when all current-version files are READY.
- `submitted_at` and `deadline_at_submission` are written server-side; late-ness is captured in AuditLog metadata and shown in staff review. The configured assignment must still be OPEN.
- All public RPCs are SECURITY INVOKER wrappers that delegate to private guarded SECURITY DEFINER implementations with pinned empty search_path. The private functions check `auth.uid()`, ACTIVE class membership, and owning Student/group or class Admin roles. Direct table access for `Submission`, `SubmissionVersion` and `File` remains revoked for web roles.
- Admin can create groups and add/remove only ACTIVE Students from the same class, with membership uniqueness for a given assignment and audit entries. Moderators can review class-submissions but cannot manage groups.
- Files are delivered through authenticated `storage.download()` only. No public bucket, public URL, service role, or persistent browser storage.

## Pages and endpoints

- `pages/submission.html?assignment=<uuid>` is the authenticated Student upload/draft/submit/version view, staff review pane, and Admin group management console.
- `js/phase3-submissions.js` handles file validation, server-issued path, private Storage upload with `upsert:false`, metadata finalization, safe failure cleanup, final submit and document downloads.
- `pages/classwork.html` links ACTIVE Students to submissions; `pages/admin-classwork.html` links Admins to assignment review.
- `public.bn_p3_prepare`, `bn_p3_finish_file`, `bn_p3_submit`, `bn_p3_cancel_file`, `bn_p3_details`, `bn_p3_groups`, `bn_p3_my_group` are the only frontend-facing submission operations.

## Acceptance gates before production sign-off

1. **Security/integration:** verify Student ownership, group membership, rejected Admin-in-Student-write, cross-class denial, unverified/signed-out denial, no public reads, oversized/unsupported MIME rejection, version status guards, full audit trail.
2. **Storage API:** create a real test Subject+Assignment using a confirmed Admin; with a confirmed ACTIVE Student upload a small harmless PDF, verify `PENDING→READY`, submit, refresh, download and check that byte contents match. Test a second version and a failed upload cleanup.
3. **Staff:** Admin and Moderator can review only their own class submissions, with no editing/deleting Student files.
4. **Groups:** Admin creates a group and adds a confirmed Student, Student uploads shared group submission, non-member cannot upload/read that group.
5. **Responsiveness:** check mobile viewport, file error messages and deadline Asia/Manila.
6. **Quota:** prevent storage abuse and routinely monitor Free Plan usage. Each version is immutable and uses space; retention/archival policies will be necessary as volume grows.
7. **Email:** Phase 1's deliverability is still on hold. Do NOT disable confirmation or make public signup claims.

**Not claimed:** Full production approval before hands-on Storage API/browser tests, antivirus scanning, or automatic orphan cleanup. A client disconnect can leave PENDING metadata; uploaders can discard it from their draft. Automated periodic cleanup and retention are future operational hardening tasks.

## Free Plan storage budgets and assignment ownership guard

Migration `20261025134536_phase3_free_storage_budget_and_assignment_guard.sql` enforces a conservative **750 MiB global metadata budget** and **200 MiB per-student budget** (both count pending and ready files not marked deleted). This reserves headroom under the Supabase Free project's storage allowance, though actual Storage usage may differ because orphan objects and platform overhead need operational monitoring. Quota checks are serialized with advisory transaction locks to prevent concurrent sessions bypassing the limit.

Phase 2 Admin changes now reject converting an existing assignment between Individual and Group when it has active groups or submissions. This protects Submission ownership invariants and historical group file access.
