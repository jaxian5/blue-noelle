# Blue Noelle audit — October 24, 2026

## Current milestone

**Phase 2: Assignments, implemented as a browser-only prototype, undergoing hardening.**
Phase 0 specification and schema draft exist. Phase 1 UI flows exist, but **production Phase 1 is not complete**: accounts, passwords, invite codes, verification and rate limits run in the browser rather than on a trusted server.

The baseline document defines the Phase 2 milestone as "Admin can create classwork; students can see it." That flow is represented in the UI. The Phase 3 true MVP upload/submission backend does not yet exist.

## Corrections in this branch

- Escape subject and assignment text before inserting into assignment-page HTML.
- Require an active Admin class membership in the Phase 2 page and browser-side assignment mutation helpers (demo guard, **not real authorization**).
- Remove fallback that treated assignments as cross-class when a class ID was missing.
- Use collision-resistant client IDs instead of bare millisecond timestamps.
- Validate deadline values and record assignment's actual class in audit entries.
- Avoid duplicate audit entries for unchanged statuses; include previous status.
- Enforce current-version and compilation source-version ownership with composite PostgreSQL foreign keys.

## Important remaining defects / gaps

1. **Critical: browser-only authentication.** `data/roles.json` publicly exposes demonstration passwords; `phase1-auth.js` stores newly registered passwords and password overrides in localStorage. Never use real user credentials on this build.
2. **Critical: browser-only authorization.** Any browser user can edit localStorage, so role/membership checks in JS are UX only. Enforce authorization in a backend before launch.
3. **Critical: no shared persistent database or storage API.** Phase 2 changes live in each browser's localStorage, so other students cannot see an admin's new assignments on their own devices.
4. **High: registration/invite limits.** Usage counting, revocation and eligibility must be atomic server-side; not reliably enforceable in localStorage.
5. **High: `submission.html` remains a Phase 3 mockup.** Navigating to an assignment does not constitute secure file submission, versioning, or download.
6. **High: draft SQL still needs DB-side guarantees** for immutable submission timestamps, non-null current version on submitted records, class-bound group ownership and relevant same-class relationships. The schema has not been exercised against a real PostgreSQL instance here.
7. **Medium: status labels and documentation drift.** README says Phase 2 complete, Phase 2 notes say started, and landing/sidebar version labels differ. They should distinguish UI-prototype milestones from production readiness.
8. **Medium: deadline editing** and `DEADLINE_CHANGED` audit are not implemented. Timezone conversion from a `datetime-local` input uses the browser's local timezone instead of explicitly treating input as Asia/Manila.
9. **Medium: unimplemented navigation** includes Schedule, Chat, Reports and Settings. Don't represent placeholders as working features.
10. **Medium: assignment data and page rendering** need browser integration tests, accessibility checks and a unified active-class selector for multi-class users.

## Recommended sequence

1. Finish Phase 1 **on a real backend**: password hashing, secure session cookies, server rate limits, PostgreSQL accounts/memberships/invites/audit.
2. Migrate Phase 2 subjects/assignments from localStorage to class-scoped REST endpoints; server-side authorization; test cross-user visibility.
3. Finish Phase 2 deadline editing, audit correctness and tests.
4. Start Phase 3: secure file uploads, storage abstraction, versions, submit/draft state, immutable timestamps and access-controlled downloads.
5. Build Phase 4 Class Clock and dashboard after the submission pipeline.

**Verification performed:** inspected repository file contents and the Phase 0 baseline; JavaScript syntax checks on changed Phase 2 scripts. **Not performed:** browser end-to-end tests, PostgreSQL migration test, backend penetration/security test.
